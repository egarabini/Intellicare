# IntelliCare LEGO — Visao Estrategica

> "Cada peca encaixa. Cada modulo gera valor. Juntos, transformam a saude."

## 1. Por Que Modularizar

O ecossistema de saude publica brasileiro e vasto e heterogeneo. Uma secretaria municipal de saude de um municipio pequeno tem necessidades completamente diferentes de um hospital universitario de referencia. Forcar todos a adotarem uma plataforma monolitica e:

- **Comercialmente inviavel** — o cliente so quer resolver SEU problema
- **Tecnicamente arriscado** — um bug em qualidade derruba o monitoramento de cronicos
- **Operacionalmente pesado** — deploy de 6 agentes quando so precisa de 1

A modularizacao transforma o IntelliCare de um "sistema grande" em uma **plataforma de modulos independentes** que se conectam quando necessario.

## 2. A Metafora LEGO

Cada modulo IntelliCare e uma peca LEGO:

- **Funciona sozinha** — tem valor independente
- **Encaixa com outras** — via contratos padronizados (FHIR, REST, eventos)
- **Nao quebra o conjunto** — remover uma peca nao derruba as outras
- **Facil de adicionar** — novo modulo = nova peca, sem refatorar o resto

### O Encaixe: FHIR R4 como Lingua Franca

Todos os modulos falam FHIR R4. Esse e o "pino" do LEGO — o contrato universal que permite que qualquer modulo se conecte a qualquer outro sem acoplamento direto.

## 5. Principios Arquiteturais

### 5.1 Independencia
Cada modulo DEVE funcionar sozinho, sem dependencia de outro modulo de agente.

### 5.2 Contrato Padronizado
Todos os modulos expoe:
- `GET /api/v1/health` — status do modulo
- `GET /api/v1/info` — metadata (nome, versao, capabilities)
- `POST /api/v1/analyze` — endpoint principal de analise (quando aplicavel)
- Eventos via Redis Streams ou HTTP webhooks (opcional)

### 5.3 FHIR-First
Dados clinicos SEMPRE trafegam como recursos FHIR R4. Nao se inventam formatos proprietarios.

### 5.4 Core Magro
O intellicare-core contem APENAS o estritamente necessario:
- FHIR client
- Modelos base compartilhados
- Configuracao e logging
- Auth helpers
- Contrato de registro de modulo

Se serve so para 1 modulo, fica naquele modulo.

### 5.5 Docker-First
Cada modulo e um container Docker. Deploy e `docker compose up`. Sem exceções.

## 6. Modelo de Evolucao

```
Fase 1 (MVP)     → core + oswaldo (rodando sozinho)
Fase 2           → + florence (analise clinica)
Fase 3           → + donabedian (qualidade)
Fase 4           → + zilda (dados brasileiros)
Fase 5           → + geralda (acompanhamento)
Fase 6           → + wanda (orquestracao)
Fase 7           → + portal (interface unificada)
```

Cada fase e um entregavel independente com valor proprio.

## 7. Origem do Codigo

Todo o codigo vem do repositorio existente `INTELLICAREREPO/`. Nao estamos reescrevendo — estamos **reorganizando e isolando** o que ja funciona.

### Mapeamento Origem → Destino

| Destino | Origem no INTELLICAREREPO |
|---------|---------------------------|
| intellicare-core | `agentes/mcp_servers/` (FHIR client, config, base) |
| intellicare-oswaldo | `agentes/oswaldo/` (engine, profiles, UI, tests) |
| intellicare-florence | `agentes/subagents/patient_iq/` + `agentes/wanda/subagents/patient_iq.py` |
| intellicare-zilda | `agentes/tools/zilda_health_data_agent.py` + `brazilian_public_data_agent.py` |
| intellicare-geralda | Novo desenvolvimento (conceito existe, codigo parcial) |
| intellicare-donabedian | Novo desenvolvimento (conceito existe, sem codigo) |
| intellicare-wanda | `agentes/wanda/` (graph, adapters, subagents, rules) |
| intellicare-portal | `PortalIntellicare/` + `backend/` |

## 8. Metricas de Sucesso

- Cada modulo roda com `docker compose up` em menos de 2 minutos
- Cada modulo tem cobertura de testes >= 80%
- Cada modulo tem documentacao funcional e tecnica completa
- Um novo desenvolvedor consegue rodar qualquer modulo em 15 minutos
- Adicionar um novo modulo nao requer mudancas nos existentes
